## Hierarchies

Lists are linear: each element has at most one successor. Many kinds of data are not linear at all. A file system has folders inside folders, an organization chart has managers with several reports, and an HTML page has elements nested inside elements. A **tree** captures this shape.

A tree consists of **nodes** connected by edges. One node, the **root**, has no parent. Every other node has exactly one parent. A node with no children is a **leaf**. The **depth** of a node is the number of edges from the root to it, and the **height** of the tree is the greatest depth of any leaf. Any node together with all of its descendants forms a **subtree**, which is itself a tree. That recursive definition is why so many tree algorithms are short recursive functions.

## Binary trees and traversal

In a **binary tree** each node has at most two children, called left and right. There are three classic depth-first ways to visit every node:

- **Pre-order**: visit the node, then the left subtree, then the right subtree. Useful for copying a tree.
- **In-order**: left subtree, node, right subtree. For a binary search tree this visits keys in sorted order.
- **Post-order**: left, right, then the node. Useful when children must be processed before their parent, such as freeing memory or evaluating an expression tree.

A **level-order** traversal visits nodes row by row using a queue, the same idea as breadth-first search.

## Binary search trees

A **binary search tree** (BST) adds an ordering rule: for every node, all keys in its left subtree are smaller than its key, and all keys in its right subtree are larger. This single rule makes searching efficient.

To **search** for a key, start at the root. If the key matches, you are done. If it is smaller, go left; if larger, go right. Repeat until you find it or fall off the tree. Each step discards an entire subtree, much like binary search discards half an array.

To **insert**, search for the key; when you fall off the tree, attach a new node at that spot. To **delete**, there are three cases. A leaf can simply be removed. A node with one child is replaced by that child. A node with two children is replaced by its **in-order successor**, the smallest key in its right subtree, which is then removed from its original position, where it has at most one child.

## Height is everything

Every BST operation follows a single path from the root, so its cost is proportional to the height of the tree. If the tree is **balanced**, with roughly equal numbers of nodes on each side at every level, the height is about log₂ n, and search, insert and delete are all O(log n). A balanced tree with a million keys is only about twenty levels deep.

The danger is that the shape depends on the insertion order. Insert the keys 1, 2, 3, 4, 5 in that order and each new key goes to the right of the previous one. The "tree" becomes a chain, its height is n, and every operation degrades to O(n), no better than a linked list. Sorted or nearly sorted input, which is common in practice, triggers exactly this worst case.

## Self-balancing trees

**Self-balancing** BSTs fix the problem by restructuring themselves after inserts and deletes. **AVL trees** keep the heights of every node's two subtrees within one of each other. **Red-black trees** use a colouring rule that keeps the longest path at most twice the shortest. Both rebalance with **rotations**, small local rearrangements of three nodes that preserve the ordering rule while changing the shape. Each guarantees O(log n) height in the worst case.

You will rarely write one from scratch. Java's `TreeMap`, C++'s `std::map` and many database indexes are built on balanced trees. What matters is knowing when to reach for one.

## Trees versus hash tables

A hash table gives O(1) average lookup, which beats O(log n). So why use a tree? Because a BST keeps keys **in order**. It can return the smallest or largest key, find the next key after a given value, and list every key in a range, all efficiently. A hash table cannot do any of these without scanning everything. If your queries involve order, such as "all appointments between 2 and 4 pm", choose a balanced tree.

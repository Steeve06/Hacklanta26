## Lookup by key

Many programs need to answer one question very quickly: given a key, what value goes with it? A username maps to an account, a word maps to its count, a course code maps to its syllabus. A **hash table** answers that question in O(1) time on average, which is why it is one of the most widely used structures in software.

## Hash functions

The idea is to turn each key into an array index. A **hash function** takes a key and returns an integer, called its hash. Taking that integer modulo the array size gives a **bucket** index. To store a pair, compute the bucket and put the pair there. To look it up later, compute the same bucket and look there.

A good hash function has three properties. It is **deterministic**: the same key always produces the same hash. It is **fast** to compute. And it **spreads keys evenly** across buckets, so that similar keys, such as `user1` and `user2`, do not end up in the same place. Real languages provide well-tested hash functions for built-in types; when you define your own key type, you usually combine the hashes of its fields.

There is one rule you must never break: if two keys are equal, their hashes must be equal. Otherwise you could store a value under one key and fail to find it with an equal key. This is why mutable objects make poor keys. If a key changes after insertion, its hash changes too, and the entry is stranded in the wrong bucket.

## Collisions

Different keys can land in the same bucket. This is called a **collision**, and it is unavoidable: there are far more possible keys than buckets. Two strategies dominate.

**Separate chaining** stores a small list in each bucket. Colliding pairs simply join the list. Lookup computes the bucket and scans its list. If keys are spread evenly, each list stays short and operations remain fast.

**Open addressing** stores every pair directly in the array. When the target bucket is taken, the table probes other slots in a fixed sequence until it finds a free one. **Linear probing** tries the next slot, then the next, and so on. It is cache-friendly but tends to form clusters, long runs of occupied slots that slow down further inserts. Deletion is also trickier, because simply emptying a slot can break the probe sequence for other keys; tables mark deleted slots with a special *tombstone* value instead.

## Load factor and resizing

The **load factor** is the number of stored entries divided by the number of buckets. As it rises, collisions become more frequent and operations slow down. Tables therefore keep the load factor below a threshold, commonly around 0.75 for chaining and lower for open addressing.

When the threshold is crossed, the table allocates a larger array, usually double the size, and **rehashes** every entry into its new bucket. Rehashing costs O(n), but like doubling a dynamic array, it happens rarely enough that inserts stay O(1) amortized.

## Costs and caveats

| Operation | Average | Worst case |
| --- | --- | --- |
| Insert | O(1) | O(n) |
| Lookup | O(1) | O(n) |
| Delete | O(1) | O(n) |

The worst case occurs when many keys collide, for example with a weak hash function or with input crafted by an attacker. Some web frameworks were once vulnerable to exactly this: a request with thousands of colliding parameter names could tie up a server. Modern languages defend against it by adding a random seed to their string hashes each time the program starts.

Hash tables also give up order. Iterating over a hash table returns entries in an order that depends on the hash values, not on insertion order or key order. Some implementations, such as Python's `dict`, additionally remember insertion order, but you cannot ask a hash table for "the smallest key" or "all keys between A and F" efficiently. For ordered queries, a balanced search tree is the right tool.

## Sets

A **hash set** is a hash table that stores only keys. It answers "have I seen this before?" in constant time, which turns many O(n²) algorithms into O(n) ones. Checking a list for duplicates by comparing every pair is quadratic; inserting each item into a set and checking membership first is linear. Spotting opportunities like this is one of the most practical skills this course aims to build.

## Nodes and pointers

A linked list stores each element in its own small object called a **node**. A node holds a value and a reference, or pointer, to the next node. The list itself only needs to remember the first node, called the **head**. The last node points to nothing, usually written `null` or `None`, which marks the end.

Because each node can live anywhere in memory, a linked list never has to copy its contents to grow. Adding an element just means creating a node and adjusting a pointer or two. That flexibility is the main reason to use one.

## Basic operations

**Inserting at the head** is the simplest operation. Create a new node, point it at the current head, then make it the new head. Nothing else in the list moves, so this takes O(1) time regardless of length.

**Inserting after a known node** is also O(1): point the new node at the old node's successor, then point the old node at the new one. The order matters. If you redirect the old node first, you lose your only reference to the rest of the list.

**Finding** an element is where linked lists struggle. There is no address arithmetic, so to reach the tenth node you must start at the head and follow nine pointers. Searching or indexing is O(n). This is the central trade-off with arrays: cheap structural changes, expensive access by position.

**Deleting** a node requires changing the pointer of the node *before* it. In a singly linked list you can only move forward, so if all you have is a reference to the node you want to remove, you must walk from the head to find its predecessor. Deleting the head itself is O(1).

## Doubly linked lists

A **doubly linked list** gives each node a second pointer, to the previous node. That costs extra memory, but it means you can delete any node in O(1) if you already hold a reference to it, and you can walk the list in both directions. The list usually also keeps a **tail** pointer, so appending at the end is O(1).

This combination is exactly what an LRU cache needs. The cache keeps items in order of last use; every time an item is read, it is unlinked from its position and moved to the front. With a hash map pointing directly at the nodes, both the lookup and the move take constant time.

## Sentinel nodes

Linked list code is full of special cases: an empty list, removing the only element, inserting before the head. A common technique is to add a **sentinel**, a dummy node that is always present and holds no real value. With a sentinel at each end, every real node always has a predecessor and a successor, so insertion and deletion use the same few lines no matter where they happen. The code becomes shorter and much harder to get wrong.

## Costs compared

| Operation | Dynamic array | Singly linked list | Doubly linked list |
| --- | --- | --- | --- |
| Access by index | O(1) | O(n) | O(n) |
| Insert at front | O(n) | O(1) | O(1) |
| Insert at end | O(1) amortized | O(n), or O(1) with tail | O(1) |
| Delete a known node | O(n) | O(n) | O(1) |
| Search | O(n) | O(n) | O(n) |

## The hidden costs

On paper a linked list looks better than an array for many operations, yet in practice arrays often win. Each node is a separate allocation, which adds memory overhead for the pointers and for the allocator's bookkeeping. Nodes are scattered across memory, so traversing a list causes many cache misses, while an array is read in neat sequential chunks. For lists of a few thousand elements, shifting an array is often faster than chasing pointers.

Use a linked list when you genuinely need constant-time insertion and removal in the middle of a sequence and already hold references to the nodes involved, as in an LRU cache, an undo history or the free list inside a memory allocator. When you only need a growable list you iterate over, a dynamic array is usually the better default.

## A note on recursion

Linked lists have a naturally recursive shape: a list is either empty or a node followed by a smaller list. Many operations, such as computing the length or reversing the list, can be written recursively in a few lines. Be careful with very long lists, though, because each recursive call uses stack space, and a list with a million nodes can overflow the call stack. An iterative loop with a couple of pointer variables avoids that problem.

## Why structure matters

A program is mostly decisions about where data lives and how you reach it. The same list of ten thousand student records can be searched in a few microseconds or in several seconds, depending only on how it is arranged in memory. A data structure is that arrangement, together with the operations you are allowed to perform on it.

It helps to separate two ideas. An **abstract data type** (ADT) describes *what* a collection does: a stack lets you push and pop, a map lets you look up a value by its key. An **implementation** describes *how* it does it: a stack can be built on top of an array or on top of a linked list. Code that only depends on the ADT can swap one implementation for another without changing. This is why most standard libraries expose interfaces such as `List` or `Map` and let you choose the concrete class separately.

## Measuring cost

To choose between implementations we need a way to talk about cost that does not depend on a particular laptop. Counting seconds is unreliable because hardware, compilers and background processes all change the result. Instead we count the number of basic steps an operation takes as a function of the input size, usually called *n*.

**Big-O notation** keeps only the part of that function that dominates as *n* grows. If an algorithm takes 3n² + 5n + 20 steps, we say it is O(n²), because for large inputs the squared term overwhelms everything else. Constant factors are dropped too: 3n² and n² are both O(n²). This is a deliberate simplification. It tells you how an algorithm *scales*, not exactly how fast it is.

The growth classes you will meet most often, from slowest-growing to fastest, are:

| Class | Name | Example |
| --- | --- | --- |
| O(1) | constant | reading the element at index 7 of an array |
| O(log n) | logarithmic | binary search in a sorted array |
| O(n) | linear | scanning a list for the largest value |
| O(n log n) | linearithmic | merge sort |
| O(n²) | quadratic | comparing every pair of items |
| O(2ⁿ) | exponential | trying every subset of a set |

The difference between these classes is dramatic. With a million items, a linear scan takes about a million steps, while binary search takes about twenty. A quadratic algorithm would need a trillion.

## Best, worst and average case

Many operations take different amounts of time depending on the input. Searching an unsorted list finishes immediately if the target is first, but must look at every element if the target is missing. We usually report the **worst case**, because it gives a guarantee. Sometimes the **average case** is more useful, for example with hash tables, where the worst case is rare in practice. When a statement such as "lookup is O(1)" is made without qualification, ask which case it refers to.

## Space is a cost too

Memory is not free. A structure that answers queries faster often does so by storing extra information. An index in a database speeds up searches but takes disk space and must be updated on every insert. A cache trades memory for time by remembering earlier answers. When you analyze a structure, note both its **time complexity** for each operation and its **space complexity**, the memory it needs as a function of *n*.

## Choosing well

Good choices start from the operations you expect to perform most often. If a program mostly appends items and occasionally reads them in order, almost any list will do. If it constantly checks whether an item is present, a hash set is likely the right tool. If it needs the smallest remaining item again and again, a heap is designed for exactly that. Throughout this course, each new structure will be introduced with the same three questions: what operations does it support, what does each operation cost, and what kind of problem makes it the natural fit?

A useful habit is to write those three answers down before writing any code. It turns a vague feeling that something is "slow" into a specific claim you can test, and it makes the trade-offs visible to the next person who reads your work.

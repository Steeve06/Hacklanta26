## Contiguous memory

An array stores its elements side by side in one continuous block of memory. Every element has the same size, so the address of element *i* can be computed directly: start address plus *i* times the element size. That single multiplication and addition is why reading or writing `a[i]` takes O(1) time no matter how large the array is. No other structure offers random access this cheaply, which is why arrays sit underneath so many others.

Contiguity also helps in a way Big-O does not capture. Modern processors load memory in chunks called cache lines. When you read one element, its neighbours usually arrive in the cache at the same time, so a loop that walks through an array in order runs much faster than a loop that jumps around memory. This effect, called **locality of reference**, often makes arrays beat structures with the same theoretical complexity.

## The fixed-size problem

A plain array is allocated with a fixed capacity. If you create space for 100 items and need a 101st, there is no guarantee that the memory right after the block is free. The only safe option is to allocate a new, larger block and copy every existing element across. Copying *n* items costs O(n), so growing by one slot at a time would make a sequence of *n* appends cost O(n²) overall.

## Dynamic arrays

A **dynamic array** (Python's `list`, Java's `ArrayList`, C++'s `vector`) hides this problem by keeping some unused capacity. It tracks two numbers: the *size*, how many elements are actually stored, and the *capacity*, how many fit in the current block. Appending writes into the next free slot and increments the size. Only when size reaches capacity does the array allocate a new block, typically **double** the old capacity, and copy everything over.

Doubling is the key idea. Suppose we start with capacity 1 and append *n* items. Copies happen when the size reaches 1, 2, 4, 8 and so on, up to *n*. The total number of elements copied is 1 + 2 + 4 + … + n, which is less than 2n. Spread across *n* appends, that is fewer than two copies per append on average. We say appending has **amortized O(1)** cost: an individual append might be slow, but any long sequence of appends is fast on average.

Growing by a fixed amount instead, say ten slots each time, does not achieve this. The copies would total roughly n²/20, which is still quadratic. The growth must be proportional to the current size. Many libraries use a factor of 1.5 rather than 2 to waste less memory; the amortized cost is still constant.

## Costs at a glance

| Operation | Cost | Why |
| --- | --- | --- |
| Read or write by index | O(1) | address arithmetic |
| Append at the end | O(1) amortized | occasional doubling |
| Insert at the front or middle | O(n) | every later element shifts right |
| Delete from the front or middle | O(n) | every later element shifts left |
| Search an unsorted array | O(n) | may need to check every element |
| Search a sorted array | O(log n) | binary search |

Insertion in the middle is the classic weakness. To make room at index *k*, every element from *k* to the end must move one place. For a large array that is a lot of copying, and it happens on every insert.

## Shrinking

When many elements are removed, a dynamic array may shrink its capacity to give memory back. Shrinking as soon as the array is half empty causes trouble: a sequence that alternates append and remove right at the boundary would grow and shrink on every operation, each time copying everything. A common fix is to shrink only when the array drops to a quarter full, and then halve the capacity. That gap keeps the amortized cost constant.

## When to use an array

Choose an array when you need fast access by position, when you mostly add and remove at the end, or when you will iterate through every element in order. Avoid it when you frequently insert or delete near the front, or when you need fast membership tests on unsorted data. In those cases the next few chapters offer better tools.

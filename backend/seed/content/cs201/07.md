## Always the most urgent item

Some problems repeatedly need the smallest or largest item from a changing collection. An emergency room treats the most serious case next. An operating system runs the highest-priority process next. A route planner explores the closest unexplored intersection next. The abstract data type for this is a **priority queue**, with two main operations: insert an item with a priority, and remove the item with the best priority.

A sorted array could do this, but every insert would shift elements and cost O(n). An unsorted array makes insert O(1) but removal O(n). A **binary heap** makes both operations O(log n).

## The heap property

A binary heap is a binary tree with two rules. First, it is **complete**: every level is full except possibly the last, which fills from left to right. Second, it satisfies the **heap property**: in a *min-heap*, every node's key is less than or equal to its children's keys. (A *max-heap* reverses the comparison.) The smallest key is therefore always at the root.

Notice what the heap property does not say. It says nothing about the order of siblings, and a heap is not sorted. It promises only that each parent beats its children. That weaker promise is cheaper to maintain.

## Stored in an array

Because a heap is complete, it can be stored in an array with no pointers at all. Put the root at index 0. For a node at index *i*, its children are at 2i + 1 and 2i + 2, and its parent is at ⌊(i − 1) / 2⌋. The tree shape is implicit in the arithmetic. This layout saves memory and keeps the data contiguous, which makes heaps fast in practice.

## Insert: sift up

To insert, place the new key in the first free slot at the end of the array, which keeps the tree complete. The heap property may now be broken between the new node and its parent. Compare them; if the new key is smaller, swap them. Repeat with the new parent until the key is no smaller than its parent or it reaches the root. This is called **sift-up**. The path from a leaf to the root has length about log₂ n, so insert costs O(log n).

## Remove-min: sift down

The minimum is at the root. To remove it, move the **last** element of the array into the root position and shrink the array by one. The tree is still complete, but the new root is probably too large. Compare it with its two children and swap it with the **smaller** child; swapping with the larger child would put that child above a smaller sibling and break the property. Repeat until the key is no larger than either child or it becomes a leaf. This **sift-down** also costs O(log n).

## Building a heap quickly

Given n items up front, you could insert them one at a time for O(n log n). There is a faster way. Put all items in an array in any order, then call sift-down on every non-leaf node, starting from the last one and moving toward the root. Most nodes are near the bottom, where sift-down travels only a step or two. Summing the work over all levels gives a total of O(n). This **heapify** step is why building a priority queue from existing data is cheap.

## Heapsort and other uses

**Heapsort** builds a max-heap, then repeatedly swaps the root with the last element and sifts down the shortened heap. It sorts in O(n log n) time with O(1) extra memory, though it is usually slower than quicksort in practice because of its scattered memory accesses.

Heaps also solve **top-k** problems efficiently. To find the 10 largest values in a stream of millions, keep a min-heap of size 10. For each new value, if it is larger than the heap's minimum, replace the minimum and sift down. The heap never grows beyond 10, so the whole pass is O(n log 10), effectively linear.

Most importantly, priority queues drive classic graph algorithms. **Dijkstra's algorithm** for shortest paths and **Prim's algorithm** for minimum spanning trees both repeatedly extract the closest unvisited vertex, and both rely on a heap to do it efficiently. You will use one in the next chapter.

| Operation | Binary heap |
| --- | --- |
| Peek at min | O(1) |
